# Environments

The template has three environments, selected by `APP_ENV`:

| `APP_ENV` | Used for | App name | Bundle id / package | Scheme | Icon |
| --- | --- | --- | --- | --- | --- |
| `development` | Local dev builds | `Expo Template (Dev)` | `com.example.expotemplate.development` | `expotemplate-development` | badged |
| `preview` | Internal QA builds | `Expo Template (Preview)` | `com.example.expotemplate.preview` | `expotemplate-preview` | badged |
| `production` | Store builds | `Expo Template` | `com.example.expotemplate` | `expotemplate` | plain |

Each environment has a different identifier, so **all three can be installed on one device side by side**.

## How it works

```
env/<APP_ENV>.env ─┐
env/local.env ─────┼─► env.ts (load + Zod validate) ─► app.config.ts ─► expo.extra.env ─► @/lib/env (runtime)
shell / EAS env ───┘
```

1. **`env.ts`** (Node, build time) reads `APP_ENV`, loads the env files and validates everything with Zod. Invalid values **stop the build or dev server** with a readable message:
   ```
   ❌ Invalid environment configuration for APP_ENV=development:
   ✖ API_URL must be a full URL, e.g. https://api.example.com
     → at client.API_URL
   ```
2. **`app.config.ts`** uses the result for the name, ids, scheme, icons and updates URL. It also embeds the **client** values into `expo.extra.env`.
3. **`@/lib/env`** (runtime) reads and re-validates `expo.extra.env`:
   ```ts
   import { Env } from '@/lib/env';
   Env.API_URL; // typed string
   Env.APP_ENV; // 'development' | 'preview' | 'production'
   ```

### Precedence (highest first)

1. Shell or EAS environment variables (`API_URL=… pnpm start`)
2. `env/local.env`: your machine only, git-ignored (copy `env/local.env.example`)
3. `env/<APP_ENV>.env`: committed defaults

### Why `env/` and not root `.env` files?

Expo CLI automatically loads root `.env`, `.env.development`, etc. based on `NODE_ENV`, not on our `APP_ENV`. With root files, `APP_ENV=preview pnpm start` would silently pick up development values. Keeping the files in `env/` means only `env.ts` loads them.

### Why not `EXPO_PUBLIC_*` variables?

Those are inlined into the JS bundle by Metro at bundle time, and they're easy to mix up across environments. Here, runtime values flow through `expo.extra.env`, which is validated in one place and is also included in EAS Update manifests.

> ⚠️ Everything in the client env ships inside the app and can be read by anyone. **Never put secrets there.** Keep secret keys on your server.

## Adding a variable

1. Add it to the env files: `env/development.env`, `env/preview.env`, `env/production.env`.
2. **Runtime value** (the app needs it): add it to `clientEnvSchema` in [`src/lib/env-schema.ts`](../src/lib/env-schema.ts), then map it in `env.ts` under `client: { … }`.
   **Build-only value** (only `app.config.ts` needs it): add it to `buildEnvSchema` in [`env.ts`](../env.ts).
3. Restart Metro with `pnpm start --clear`.

## Strict mode

Some values are only required when producing a real binary. **Strict mode** is on when `STRICT_ENV_VALIDATION=1` (all `prebuild` scripts) or `EAS_BUILD=true` (EAS cloud builds). In strict mode, `preview` and `production` require `EAS_PROJECT_ID`. A fresh clone can still run `pnpm start` without an Expo account.

## Build profiles (`eas.json`)

| Profile | Distribution | Channel | `APP_ENV` | Notes |
| --- | --- | --- | --- | --- |
| `development` | internal | `development` | development | Dev client (`expo-dev-client`) |
| `development-simulator` | internal | `development` | development | iOS simulator build |
| `preview` | internal | `preview` | preview | Android APK for easy QA install |
| `production` | store | `production` | production | Android App Bundle; auto-increments build number |

Each profile's **channel** decides which OTA updates that binary receives (see the OTA guide in Phase 5). `runtimeVersion` uses the **fingerprint** policy: when native code changes, the runtime version changes automatically, and older binaries ignore incompatible updates.

## Badged icons

Development and preview builds show a banner (`development` / `preview`) and a version ribbon on the launcher icon. These are generated by `pnpm icons:badge` into `assets/*-development.png` and `assets/*-preview.png`, and are committed. Re-run it after changing the base icons or the `version` in `package.json`.

> The `app-icon-badge` *config plugin* is deliberately not used. It writes icons without waiting for them to finish, which races the Android icon step during EAS builds.

## Local Android builds and memory

The generated `android/gradle.properties` normally gives Gradle a 2 GB heap, which fails with `Java heap space` in `:app:mergeDebugResources`. The local config plugin [`plugins/with-gradle-memory.js`](../plugins/with-gradle-memory.js) raises it to 4 GB on every prebuild. On a machine with less than 8 GB of RAM, lower `-Xmx` there.
